Security

Client and server trade keys in a handshake

Each side made a 2048-bit RSA key pair. The client sent its public key, and the server answered with its own. A fingerprint is a short hash of a key: when two fingerprints match, the keys are the same.

A login sent in a sealed envelope

The client encrypts the user and the password with the public key of the server (RSA-OAEP with SHA-256). Only the private key of the server can open it. The demo account is admin with the password chatuba.

    How it works
    
      
    
        
    
          
    The handshake
    
          
    The client calls Products.Handshake with its public key in the PKIX format. The server keeps it for the connection, and replies with its own public key. The server refuses keys smaller than 2048 bits.
    
        
    
        
    
          
    The sealed login
    
          
    The client writes {"user", "password"} as JSON and encrypts it with RSA-OAEP. The ciphertext is 256 bytes, and it is different each time. The server compares the hashes in constant time, and allows three failed tries on each connection.
    
        
    
        
    
          
    One session for each connection
    
          
    The server registers a new service for each connection, so a login is valid only on its own connection. The catalog is shared by all connections, and a lock protects it.
    
        
    
        
    
          
    The wire
    
          
    net/rpc encodes each call with encoding/gob. Gob sends the definition of a type the first time that the type is used, so the first call of a kind is larger. Only the login is encrypted. Use TLS to protect the other calls.
